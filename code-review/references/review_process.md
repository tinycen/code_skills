# 代码审查流程与规则

本文件定义代码审查的完整流程、检查维度和问题分级标准。

---

## 跳过废弃 / 旧文件与文件夹（前置过滤规则）

> **原则**：代码审查应聚焦于当前活跃、维护中的代码。对于用户已明确标记为废弃、归档或遗留的文件/文件夹，应在扫描阶段直接排除，不进入后续审查流程。

### 自动跳过的目录（固定命名）

以下名称的目录（不区分大小写）及其内部所有内容，**自动跳过**：

| 类别 | 目录名（示例） |
|------|---------------|
| 废弃/弃用 | `deprecated`, `deprecated_files`, `deprecated_code`, `obsolete`, `obsolete_files`, `废弃`, `废弃代码`, `弃用`, `弃用代码` |
| 旧文件 | `old_file`, `old_files`, `old`, `old_code`, `旧文件`, `旧代码`, `旧版` |
| 遗留代码 | `legacy`, `legacy_code`, `遗留`, `遗留代码` |
| 归档/备份 | `archive`, `archives`, `archived`, `bak`, `backup`, `backups`, `归档`, `备份`, `备份文件` |
| 参考文档 | `references`, `reference`, `参考文档`, `参考`, `参考材料` |

### 用户自定义跳过标记

用户可在仓库根目录或任意子目录下放置以下标记文件，以声明该目录内需要跳过的文件或子目录：

- **标记文件名**：`.code_review_ignore` 或 `.cr_skip`
- **格式**：每行一个条目（相对于标记文件所在目录的路径），支持 `*` 通配符。以 `#` 开头的行为注释。
- **示例**（`.code_review_ignore`）：
  ```
  # 以下文件/目录不参与代码审查
  old_impl.py
  temp/
  *.draft.js
  deprecated_modules/
  ```

### 自动跳过的文件（固定命名前缀）

文件名以以下前缀开头（不区分大小写）的文件，**自动跳过**：
- `deprecated_`
- `old_`
- `legacy_`
- `obsolete_`
- `archive_`
- `bak_`

### 过滤执行规则

- 过滤操作在**代码扫描阶段之前**执行，被过滤掉的文件/目录不进入统计、不进入问题检测、不写入报告。
- 若因过滤导致某检查维度无文件可审（如所有 Python 文件均在废弃目录中），直接跳过该维度，不报错。
- 审查报告头部统计信息中，**不体现**被过滤文件的数量（仅统计实际参与审查的文件）。

## 已忽略与误报问题去重与报告归档

### 已忽略与误报问题去重（防重复报告）

每次审查前，先从 `docs/code_reviews/fixed/` 目录扫描用户已整理的报告，提取其中标记为「忽略」或「误报」的问题，更新到 `ignored_issues.md`。

- **扫描范围**：仅扫描 `docs/code_reviews/fixed/` 目录下的报告文件，不扫描根目录下的新生成报告（避免未处理报告中的标记被误读）。
- **加载清单**：然后加载 `ignored_issues.md`，提取已忽略与误报问题列表供审查过滤使用。
- **匹配规则**：审查过程中发现的问题若与清单中的条目在「文件路径 + 问题标题」上匹配（标题相似度 ≥ 80% 或完全一致，且文件路径相同），则跳过该问题，不纳入统计、不写入报告。
- **忽略标记识别规则**：问题标题中包含 `（忽略）` / `(ignore)` / `(IGNORE)` / `【忽略】` / `[忽略]` / `[IGNORE]` / `[ignore]` 等；或问题描述/修复建议中明确包含「忽略此问题」「忽略」「不修复」「已知问题，暂不处理」「ignore this issue」「won't fix」等显式声明。
- **误报标记识别规则**：问题标题中包含 `（误报）` / `(false positive)` / `(FALSE POSITIVE)` / `(FP)` / `(fp)` / `【误报】` / `[误报]` / `[FALSE POSITIVE]` / `[fp]` 等；或问题描述/修复建议中明确包含「误报」「false positive」「工具误判」「非问题」「not an issue」「not a real issue」等显式声明。
- **标记优先级**：若同一问题同时包含忽略与误报标记，优先识别为「误报」（误报比忽略更彻底地否定问题存在性）。
- **追加时去重**：按「文件路径 + 问题标题」检查是否已存在于清单，已存在则跳过，避免重复写入。
- **恢复跟踪**：如用户需恢复跟踪某已忽略或误报问题，可手动从 `ignored_issues.md` 中删除对应条目，下次审查将重新报告。

### 报告归档机制（`fixed/` → `archived/`）

- 用户查看报告后，将已确认处理（标记了忽略、误报或修复了问题）的报告移至 `fixed/` 目录（`fixed/` 视为「待扫描收件箱」）。
- 工具在审查前扫描 `fixed/` 提取忽略与误报标记后，**自动把 `fixed/` 下全部报告移动到 `archived/` 目录**，使 `fixed/` 保持为空。
- 下次审查仅扫描用户新放入 `fixed/` 的报告，避免对历史报告重复扫描。
- `ignored_issues.md` 中「原报告」字段只记录文件名，对应文件已归档于 `docs/code_reviews/archived/` 子目录。

## 审查流程

### 整体流程

```
1. 代码扫描
   ├── 文件结构分析（过滤后）
   ├── 依赖关系分析（过滤后）
   └── 代码统计（过滤后）

2. 问题检测
   ├── 命名规范检查
   ├── 命名合理性检查
   ├── 方法逻辑检查
   ├── 代码质量检查
   ├── 依赖管理检查
   └── 项目结构与目录划分检查

3. 问题分类
   ├── 🔴 严重bug (CRITICAL)
   ├── 🟠 注意问题 (WARNING)
   ├── 🟡 一般问题 (INFO)
   └── 🟢 轻微问题 (MINOR)

4. 报告生成
   ├── 汇总统计
   ├── 详细问题列表
   └── 优化建议
```

## 检查维度

### 1. 命名规范检查

#### 变量命名
- **检查项**：变量名是否符合语言规范（Python: snake_case, Java/C#/TypeScript/JavaScript/Dart: camelCase, Go: camelCase）
- **检查项**：变量名是否有意义，避免使用单字母或无意义名称
- **检查项**：常量是否使用全大写命名（Python/Go），或 PascalCase（C#/TypeScript/JavaScript/Dart）
- **检查项**：布尔变量是否使用 is/has/can 等前缀（Python/Java/C#/TypeScript/JavaScript），Go 中避免此类前缀

#### 方法命名
- **检查项**：方法名是否使用动词开头
- **检查项**：方法名长度是否适中（2-4个单词）
- **检查项**：私有方法是否使用下划线前缀（Python/Dart），或使用 private 访问修饰符（Java/C#/TypeScript/JavaScript）

#### 类命名
- **检查项**：类名是否使用 PascalCase
- **检查项**：抽象类是否使用 Abstract 前缀（C#/Java），Dart 中使用 `abstract class` 无额外前缀
- **检查项**：接口是否使用 I 前缀（C#），或使用 PascalCase 描述能力（Java/TypeScript/JavaScript），Go 中接口名常以 -er 结尾（如 Reader, Writer），Dart 中接口与抽象类同为 `abstract class`，无特殊标记

#### 文件夹与包命名
- **检查项**：文件夹名是否符合语言/生态规范（Python 包: snake_case，Java 包: 全小写反向域名如 `com.example.module`，Go 包: 小写单词无下划线，Node.js/TypeScript 项目: kebab-case 或 camelCase，.NET 项目: PascalCase）
- **检查项**：文件夹/包名是否简洁且具有描述性，能体现模块职责
- **检查项**：是否存在层级过深的目录结构（建议不超过 3-4 层）
- **检查项**：同一层级文件夹的命名风格是否统一（不混用 snake_case 与 camelCase）

#### 命名一致性
- **检查项**：同一概念是否使用相同命名
- **检查项**：缩写是否保持一致
- **检查项**：中英文是否混用

#### 英文拼写检查
- **检查项**：标识符（变量、方法、类、文件名等）中的英文单词拼写是否正确
- **检查项**：注释、文档字符串、日志文本中的英文拼写是否正确
- **检查项**：是否统一使用英式或美式拼写（如 colour/color、initialize/initialise）
- **检查项**：缩写是否为项目或行业内通用，避免自创或生僻缩写
- **检查项**：同一概念是否使用相同缩写，避免混用（如 `user` 与 `usr`）

---

### 2. 命名合理性检查

> 本维度关注命名的**语义准确性**，即名称是否真实反映其职责、行为或内容，而非仅检查格式规范。

#### 变量语义
- **检查项**：变量名是否准确表达其存储的数据含义（如 `userCount` 而非 `num`，`orderList` 而非 `data`）
- **检查项**：变量名是否与其实际类型/内容一致（如名为 `list` 的变量实际是字典，名为 `id` 的字段实际存的是名称）
- **检查项**：是否存在误导性命名（名称暗示某种含义，但实际用途完全不同）
- **检查项**：是否有更清晰、更具表达力的替代名称

#### 方法语义
- **检查项**：方法名是否准确描述其执行的行为（如 `getUser` 实际做的是删除操作）
- **检查项**：方法名是否与其副作用一致（名为 `getX` 的查询方法是否产生了写操作）
- **检查项**：方法名是否与其返回值类型/含义一致（如 `isValid` 返回的不是布尔值）
- **检查项**：方法重载或同名方法在不同类中的语义是否保持一致

#### 类与模块语义
- **检查项**：类名是否准确概括其职责范围（如 `UserManager` 是否只做用户管理，还是混入了权限、日志等无关逻辑）
- **检查项**：模块/包名是否与其实际提供的功能一致（如 `utils` 包是否真的都是工具函数，还是混入了业务逻辑）
- **检查项**：文件夹/目录名是否反映其包含模块的真实职责（如 `common` 目录是否变成了垃圾桶）

#### 命名可理解性
- **检查项**：对于新接触代码的开发者，名称是否易于理解，无需深入阅读实现即可把握意图
- **检查项**：是否存在过度缩写或晦涩的命名（如 `usrMgrCtrl` 不如 `userManagerController` 直观）
- **检查项**：同一项目内，相同概念是否使用了不同的名称（如同一实体在不同文件中叫法不同）
- **检查项**：是否存在「万能命名」滥用（如 `data`、`info`、`handler`、`manager`、`utils` 等过于笼统的名称）

### 3. 方法和逻辑检查

#### 方法设计
- **检查项**：方法长度是否超过 50 行
- **检查项**：方法参数是否超过 5 个
- **检查项**：方法职责是否单一（SRP）
- **检查项**：是否存在重复代码

#### 逻辑正确性
- **检查项**：边界条件是否处理
- **检查项**：空值检查是否完整
- **检查项**：异常处理是否恰当
- **检查项**：循环是否有终止条件
- **检查项**：方法调用是否正确（参数类型/数量、调用顺序、废弃方法）
- **检查项**：类型转换是否安全
- **检查项**：并发安全问题（竞态条件、死锁风险）

#### 资源管理
- **检查项**：文件句柄是否正确关闭
- **检查项**：数据库连接是否正确释放
- **检查项**：锁/信号量是否正确释放
- **检查项**：网络连接/线程池是否正确关闭

#### 代码复杂度
- **检查项**：嵌套层级是否超过 3 层
- **检查项**：条件分支是否过多
- **检查项**：圈复杂度是否过高

### 9. 项目结构与目录划分检查

> 本维度关注项目整体目录布局是否清晰、是否符合所在框架/生态的常规实践，以及不同功能的文件是否被划分到了合理的目录中。
> 适用于 FastAPI、Django、Next.js、React 等具有明确目录约定或推荐结构的项目。
> 详见 [language_checks/project_structure_check.md](language_checks/project_structure_check.md)

#### 目录职责

- **检查项**：同一目录内的文件是否围绕同一职责，避免「万能目录」变成垃圾桶
- **检查项**：业务模块、工具函数、配置、测试、静态资源等是否各归其位
- **检查项**：目录层级是否过深（建议不超过 3-4 层）

#### 框架结构合规性

- **检查项**：FastAPI 项目是否按 `routers/`、`models/`、`schemas/`、`services/` 等常规方式组织
- **检查项**：Django 项目是否遵循 project/app/templates/static/migrations 的默认结构
- **检查项**：Next.js / React 项目是否区分路由页面、可复用组件、公共工具、钩子、类型定义等目录
- **检查项**：API 路由与页面路由是否清晰分离

#### 入口与可理解性

- **检查项**：项目入口文件是否明确且位置合理
- **检查项**：对于新接触代码的开发者，目录结构是否易于理解

## 问题分级标准

### 🔴 严重bug (CRITICAL)

**定义**：必须立即修复的严重问题，可能导致程序崩溃、数据丢失或安全漏洞。

**典型问题**：
- 空指针引用
- 数组越界
- 死循环
- SQL 注入漏洞
- 敏感信息泄露
- 资源未释放（内存泄漏、文件句柄泄漏）
- 并发竞态条件
- 项目结构错误导致运行失败（如 Next.js 页面放错目录、Django app 未注册）

**处理方式**：
- 立即修复
- 修复后需要重新测试
- 必须在发布前解决

---

### 🟠 注意问题 (WARNING)

**定义**：需要关注的问题，可能影响程序稳定性或可维护性。

**典型问题**：
- 异常处理不当（捕获后忽略）
- 硬编码配置值
- 重复代码块
- 过长的方法或类
- 缺少必要的输入验证
- 不安全的类型转换
- 业务逻辑泄漏到通用目录（如 `utils/` 混入大量业务代码）

**处理方式**：
- 尽快修复
- 制定修复计划
- 建议在当前迭代解决

---

### 🟡 一般问题 (INFO)

**定义**：代码质量问题，建议优化以提高可读性和可维护性。

**典型问题**：
- 命名不规范
- 缺少注释
- 代码结构混乱
- 未使用的变量或导入
- 方法参数过多
- 复杂的条件表达式
- 目录层级过深或测试文件位置不一致

**处理方式**：
- 建议优化
- 可在后续迭代改进
- 重构时一并处理

---

### 🟢 轻微问题 (MINOR)

**定义**：代码风格问题，建议改进以保持一致性。

**典型问题**：
- 缩进不一致
- 空行使用不规范
- 注释格式不统一
- 代码对齐问题
- 尾随空格
- 空目录残留或个别文件命名与所在目录风格不一致

**处理方式**：
- 建议改进
- 可通过 IDE 自动修复
- 代码格式化时处理

## 审查执行步骤

### 步骤 0：废弃/旧文件过滤（前置）

在执行代码扫描前，先识别并排除用户标注的废弃/旧文件与文件夹。

```bash
# 生成排除参数（废弃目录固定命名 + 用户标记文件）
SKIP_DIRS=(deprecated deprecated_files deprecated_code obsolete obsolete_files old_file old_files old old_code legacy legacy_code archive archives archived bak backup backups 废弃 废弃代码 弃用 弃用代码 旧文件 旧代码 旧版 遗留 遗留代码 归档 备份 备份文件 references reference 参考文档 参考 参考材料)
SKIP_ARGS=""
for d in "${SKIP_DIRS[@]}"; do
  SKIP_ARGS="$SKIP_ARGS -not -path '*/$d/*'"
done

# 读取用户标记文件并追加排除（.code_review_ignore / .cr_skip）
# 标记文件格式：每行一个相对路径，支持 * 通配符，# 开头为注释
while IFS= read -r line; do
  [[ "$line" =~ ^#.*$ ]] && continue
  [[ -z "$line" ]] && continue
  SKIP_ARGS="$SKIP_ARGS -not -path '*/$line'"
done < <(find <仓库路径> -maxdepth 2 \( -name ".code_review_ignore" -o -name ".cr_skip" \) -type f -exec cat {} + 2>/dev/null)

# 标记文件本身也不参与审查
SKIP_ARGS="$SKIP_ARGS -not -name '.code_review_ignore' -not -name '.cr_skip'"
```

> **说明**：`SKIP_ARGS` 变量需在后续所有 `find` 命令中原样展开使用，以统一排除废弃内容。若仓库无废弃目录/标记文件，该变量为空，不影响正常扫描。

### 步骤 1：代码扫描

```bash
# 统计代码行数（支持多种语言）
find <仓库路径> $SKIP_ARGS \( -name "*.py" -o -name "*.js" -o -name "*.ts" -o -name "*.java" -o -name "*.go" -o -name "*.rs" \) -type f | xargs wc -l

# 查找配置文件
find <仓库路径> $SKIP_ARGS \( -name "requirements*.txt" -o -name "setup.py" -o -name "pyproject.toml" -o -name "setup.cfg" -o -name "Pipfile" \) -type f

# 查找 YAML/YML 配置文件
find <仓库路径> $SKIP_ARGS \( -name "*.yaml" -o -name "*.yml" \) -type f

# 查找 JSON 配置文件
find <仓库路径> $SKIP_ARGS -name "*.json" -type f | grep -v node_modules | grep -v __pycache__ | grep -v .git

# 查找 TOML 配置文件
find <仓库路径> $SKIP_ARGS -name "*.toml" -type f

# 查找环境配置文件
find <仓库路径> $SKIP_ARGS -name ".env*" -type f

# 查找 Dockerfile 和 docker-compose
find <仓库路径> $SKIP_ARGS \( -name "Dockerfile*" -o -name "docker-compose*" \) -type f
```

### 步骤 2：问题检测

按检查维度逐项检查，记录问题位置和描述。
- 若仓库中不存在某类文件（如无 YAML 配置文件），则跳过对应维度的检查。
- 若项目为无明确框架结构的纯脚本或辅助代码集合，可跳过「项目结构与目录划分检查」。

### 步骤 3：问题分类

根据问题严重程度分级：
- 🔴 严重Bug：必须修复
- 🟠 注意问题：建议修复
- 🟡 一般问题：可优化
- 🟢 轻微问题：建议改进

### 步骤 4：生成报告

按照 `templates/report.md` 模板生成审查报告。

**报告生成规则**：
- 必须包含**截止提交**信息（最新 commit hash 与 commit message）
- **空分类隐藏**：如果某个级别没有问题，报告中不展示该级别的板块，仅输出有问题级别的详细内容
- **不含质量评分**：报告中不包含任何维度的百分制评分或综合评分。代码审查应聚焦于具体问题与修复建议，避免主观打分
- **不含改进计划/排期**：报告中不包含按周或按优先级划分的时间排期与工时估算。修复优先级由问题分级体现，具体排期由团队自行决策
- **不含总结与建议板块**：报告头部已包含问题统计，足以体现整体情况。禁止在报告末尾添加【总结与建议】板块，避免冗余的抽象评价与重复内容

## 审查注意事项

- 审查应基于代码实际内容，而非个人偏好
- 问题描述应具体，包含文件路径和行号
- 提供修复建议，而非仅指出问题
- 关注代码的整体质量，而非细节吹毛求疵
- 尊重原作者的代码风格，在一致性基础上提建议
