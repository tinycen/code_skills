# 跨仓库联调一致性检查

本文件定义前后端跨仓库审查中，除单仓代码质量之外的**联调一致性检查维度、匹配策略与问题分级标准**。

> 单仓代码质量检查（命名、逻辑、规范、安全等）仍按 [review_process.md](review_process.md) 执行，不在本文件重复。

---

## 检查范围

本检查关注前端仓库与后端仓库之间**接口契约、数据流转、约定语义**的一致性。检查对象包括但不限于：

- 前端 HTTP 请求代码（如 `fetch`、`axios`、`request`、`useApi` 等封装）。
- 前端类型定义（TypeScript interfaces/types）。
- 前端生成的 API Client 代码。
- 前端 Mock 数据/服务（存在时）。
- 后端路由定义（如 FastAPI/Flask/Django/Express/Spring 等框架的路由装饰器或配置文件）。
- 后端请求模型/校验模型（如 Pydantic、DTO、Serializer）。
- 后端响应模型/序列化模型。
- 后端 OpenAPI / Swagger / 接口定义文件（自动发现）。
- 后端错误处理与状态码返回逻辑。

---

## 问题分级标准

联调一致性问题沿用 [review_process.md > 问题分级标准](review_process.md#问题分级标准)，但结合跨仓场景重新定义典型问题：

### 🔴 严重bug (CRITICAL)

可能导致功能不可用、数据错误或安全漏洞的联调不一致。

- 前端调用的 API 路径或 HTTP 方法在后端不存在。
- 后端删除了接口但前端仍在调用。
- 必填请求字段前端未传递，导致后端校验必败。
- 后端返回字段类型与前端正向处理逻辑严重不符（如前端按数组处理，后端返回对象）。
- 鉴权字段（Token、Header）传递方式不一致导致未授权或安全问题。
- 后端 OpenAPI 定义与实际路由实现不一致，导致生成类型严重错误。

### 🟠 注意问题 (WARNING)

可能影响稳定性或可维护性的不一致。

- 前端请求参数命名与后端不一致（如 `userId` vs `user_id`）。
- 可选字段默认值前后端理解不一致。
- 错误码/错误提示字段命名或取值范围不一致。
- 分页参数命名不一致（如 `pageSize` vs `limit`）。
- 前端生成的 API Client 类型与后端实现存在字段差异（生成文件过期）。
- 响应中同一业务实体的字段命名前后端不统一。

### 🟡 一般问题 (INFO)

建议优化以提高协作效率的一致性问题。

- 同一概念在前后端使用了不同缩写（如 `user` vs `usr`）。
- 枚举值顺序或表述不一致。
- 状态码使用习惯不统一（如后端用 200 包裹错误，前端期望 4xx）。
- Mock 数据字段比真实后端多/少，但尚未影响功能。
- 响应字段冗余：后端返回了前端未使用的字段，或前端期望的字段未在接口文档中声明。

### 🟢 轻微问题 (MINOR)

风格或约定层面的轻微差异。

- 布尔字段命名前缀不一致（如 `isActive` vs `active`）。
- 时间戳字段格式不一致（如秒级 vs 毫秒级），但两端实际能正常处理。
- URL 路径大小写、尾部斜杠等风格差异。

## 检查维度

### 1. API 路由与方法一致性

- 前端调用的每个 API 路径、HTTP 方法是否能在后端找到对应路由。
- 是否存在前端调用而后端未暴露的接口。
- 是否存在后端已暴露但前端未使用的接口（可选提示，不作为必报问题）。
- URL 路径风格是否一致（如 kebab-case vs camelCase、是否带版本前缀 `/v1/`）。

### 2. 请求参数一致性

- 必填字段是否一致：后端标记为必填的字段，前端是否都传递。
- 字段命名是否一致：同一参数在前后端名称是否相同。
- 字段类型是否一致：字符串、数字、布尔、数组、对象等。
- 参数传递位置是否一致：path / query / header / body。
- 默认值与枚举值是否一致。
- 日期/时间格式是否一致（如 ISO 8601、Unix 秒/毫秒）。

### 3. 响应结构一致性

- 前端使用的响应字段是否在后端响应模型中存在。
- 响应字段类型是否一致（特别关注数字、字符串、null 的处理）。
- 嵌套结构是否一致（如 `data.user.name` vs `data.username`）。
- 数组元素结构是否一致。
- 空值与缺省字段处理是否一致：后端不返回 vs 返回 `null` vs 返回空值。

### 4. 状态码与错误格式一致性

- 成功状态码约定是否一致（如 200、201、204 的使用场景）。
- 错误状态码约定是否一致（如 400、401、403、404、500 的使用场景）。
- 错误响应体结构是否一致：错误码字段、错误消息字段、详细错误字段。
- 错误码枚举是否一致：同一业务错误在前后端是否有相同含义的错误码。

### 5. 类型 / Codegen 一致性

- 后端 OpenAPI / Swagger 文件是否存在且有效。
- OpenAPI 定义是否与后端实际路由、请求模型、响应模型一致（检查定义文件是否过期）。
- 前端是否基于 OpenAPI 生成了 TypeScript 类型 / API Client。
- 生成文件是否与后端 OpenAPI 定义同步：字段、类型、必填标记是否一致。
- 若前端未使用生成文件，而是手写类型，则检查手写类型与后端实现的一致性。

### 6. 鉴权与权限一致性

- Token 传递方式是否一致：Header 名称（如 `Authorization` vs `X-Token`）、前缀（`Bearer ` vs 无前缀）、Cookie 等。
- Token 刷新机制是否一致：刷新时机、刷新接口、并发请求处理。
- 权限字段命名与取值是否一致：如角色、权限码在前后端的定义。
- 未授权/权限不足的处理是否一致：跳转登录、弹窗提示、静默刷新等。

### 7. 分页 / 过滤 / 排序约定一致性

- 分页参数命名是否一致：`page`/`size`、`offset`/`limit`、`cursor` 等。
- 分页返回值结构是否一致：总条数字段、当前页字段、数据列表字段。
- 过滤参数传递方式是否一致：query string、body、数组格式等。
- 排序参数命名与格式是否一致：`order_by`、`sort`、`sort_field` + `sort_order`。

### 8. 命名与语义对齐

- 同一业务实体在前后端的命名是否一致：如 `User`、`Account`、`Member`。
- 同一字段的命名是否一致：如 `phoneNumber` vs `mobile` vs `tel`。
- 同一枚举值的命名与取值是否一致：如状态 `active`/`inactive` vs `1`/`0`。
- 缩写是否统一：避免 `user`/`usr`、`order`/`ord` 等混用。

### 9. Mock 与真实 API 一致性

> 本维度仅在前端仓库存在 Mock 数据/服务时执行；不存在时跳过。

- Mock 接口路径、方法是否与真实后端一致。
- Mock 响应字段是否与后端响应模型一致。
- Mock 状态码与错误响应格式是否与后端一致。
- 是否存在仅 Mock 支持而真实后端未返回的字段（可能导致联调通过后上线失败）。
- 是否存在真实后端已变更但 Mock 未同步更新的情况。

## 匹配策略

### 前后端接口如何配对

1. **URL 路径 + HTTP 方法优先**：前后端路径片段一致（忽略版本前缀、尾部斜杠、大小写差异）且方法一致时，视为同一接口。
2. **OpenAPI 定义辅助**：若后端存在 OpenAPI 文件，优先以 OpenAPI 中定义的 `operationId` 或路径作为权威契约，再匹配前端调用点。
3. **模糊匹配**：路径相似但命名风格不同（如 `/user-list` vs `/users`）时，作为潜在不一致提示，标记为 WARNING 或 INFO。
4. **未匹配项**：前端调用点未匹配到后端路由时，标记为 CRITICAL；后端路由未匹配到前端调用点时，可作为 INFO 提示资源闲置或文档缺失。

### 字段如何配对

- 名称完全一致的字段直接配对。
- 名称不同但语义明显一致的字段（如 `userId` 与 `user_id`）作为潜在不一致提示。
- 后端必填但前端未提供的字段，直接标记为不一致。
- 前端使用但后端未定义的字段，标记为不一致。

---

## 检查执行注意事项

- 联调检查应基于代码实际内容，避免依赖假设。
- 发现不一致时，问题描述需同时给出前端文件路径/行号与后端文件路径/行号。
- 对于 OpenAPI / 生成文件过期问题，需明确指出“定义文件最后修改时间”与“后端实现最后修改时间”的差异。
- 对于 Mock 数据问题，需说明是哪份 Mock 文件与哪条后端路由不一致。
- 问题分级应结合业务影响：影响功能必达路径的归为 CRITICAL，约定不一致但功能正常的归为 INFO 或 MINOR。
