# 工作流三：前后端跨仓库联调审查

本文件定义同时对前端仓库与后端仓库执行联调一致性审查的完整流程。

> 本工作流复用现有单仓审查能力：先分别对前后端执行单仓审查，再执行跨仓联调一致性检查，最终输出三份独立报告（前端单仓报告、后端单仓报告、联调报告）。
> 具体单仓执行规范引用 `references/review_process.md`，保存与分发规则引用 `references/report_delivery.md`。

---

## 触发条件

必须**同时满足**以下两个条件才使用本工作流：

1. 用户**显式指明**了两个仓库的前后端对照关系，例如：
   - “审查前后端联调一致性。”
   - “检查前端仓库 X 和后端仓库 Y 的接口是否对得上。”
   - “看看前端请求和后端返回是否一致。”
2. 提供了前端仓库与后端仓库的地址/路径，或定时任务配置中同时指定了这两个仓库。

> **重要**：仅因用户一次提供了两个仓库地址，**不得**自动推断为前后端关系。未显式声明对照意图时，应分别走[工作流一：手动触发](manual_workflow.md)或[工作流二：定时触发](scheduled_workflow.md)。

---

## 输入参数

| 参数 | 必填 | 说明 |
|------|------|------|
| 前端仓库地址/路径 | 是 | SSH 地址（如 `git@github.com:org/frontend.git`）或本地绝对路径。 |
| 后端仓库地址/路径 | 是 | SSH 地址（如 `git@github.com:org/backend.git`）或本地绝对路径。 |
| 主仓库（报告保存目标） | 否 | 用户可指定报告保存到前端或后端仓库。 |

以下**不作为输入参数**，由审查过程中自动发现：

- **后端 OpenAPI / Swagger / 接口定义文件**：扫描常见位置自动定位，并校验是否与后端实际路由/模型一致。
- **前端 API Client 生成目录/文件**：扫描常见生成目录自动定位，并校验是否与实际后端实现同步。
- **前端 Mock 数据/服务**：扫描常见 mock 目录自动定位，仅在存在时参与审查。

## 执行步骤

### 步骤 1：参数识别与触发条件校验

- 确认用户显式要求执行前后端联调审查。
- 确定前端仓库与后端仓库的地址/路径。
- 确定主仓库（用户指定 → 当前目录所在仓库 → 问题数量更多的仓库 → 默认后端仓库）。

> 主仓库推导规则详见 [references/report_delivery.md > 跨仓库联调审查报告保存规则](../references/report_delivery.md#跨仓库联调审查报告保存规则)。

### 步骤 2：自动发现辅助文件

- **后端**：扫描常见 OpenAPI / Swagger / 接口定义文件位置：
  - `openapi.yml`, `openapi.yaml`, `openapi.json`
  - `docs/openapi.*`, `api/schema/*`, `swagger.*`
- **前端**：扫描常见 API Client 生成目录/文件：
  - `src/api/generated/`, `src/services/`, `src/api/`, `api/`
  - 包含 `*.generated.ts`, `*Api.ts`, `*Client.ts` 等生成文件
- **前端 Mock**：扫描常见 mock 目录/文件：
  - `src/mock/`, `mock/`, `__mocks__/`, `msw/`, `vite-plugin-mock/`
  - 若不存在任何 mock 数据/服务，跳过 Mock 一致性检查维度。

发现多个候选文件时，按文件大小、修改时间、路径匹配度选择最可能的一份，并在报告中记录实际使用的文件路径。

### 步骤 3：获取远程代码（仅远程场景执行）

按 [references/repository_access.md](../references/repository_access.md) 分别对前端仓库和后端仓库执行：

- GitHub SSH 密钥检查与配置（仅 GitHub）。
- 检查目标本地绝对路径是否已存在仓库代码。
- 若已存在：执行更新本地仓库。
- 若不存在：执行克隆仓库。
- 若克隆/推送过程中因权限被拒绝：执行 GitHub SSH 权限重试。
- 记录实际来源方式。

### 步骤 4：获取版本信息

按 [references/repository_access.md > 版本信息获取](../references/repository_access.md#版本信息获取) 分别执行：

- 获取前端最新 tag 版本号与最近提交信息（截止提交）。
- 获取后端最新 tag 版本号与最近提交信息（截止提交）。

### 步骤 5：扫描已整理报告并更新已忽略与误报问题清单

分别对前端仓库和后端仓库执行：

- 扫描各自 `docs/code_reviews/fixed/` 目录下的报告文件。
- 提取标记为「忽略」或「误报」的问题，去重后追加到各自仓库的 `ignored_issues.md`。
- 扫描完成后将 `fixed/` 下全部报告移动到 `archived/`。
- 若归档失败：记录失败原因并继续审查流程，在最终通知中说明。

> 注意：跨仓审查的忽略与误报清单最终统一保存到主仓库，但去重来源需同时覆盖前端与后端的单仓忽略与误报记录。

### 步骤 6：加载已忽略与误报问题清单

- 加载前端仓库的 `ignored_issues.md`。
- 加载后端仓库的 `ignored_issues.md`。
- 合并去重后作为本次审查的忽略与误报清单来源。

> **并行执行提示**：环境支持子代理时，从本步骤开始可按照 [strategies/subagent_strategy.md](strategies/subagent_strategy.md) 并行派发前端单仓审查、后端单仓审查与跨仓联调一致性检查。各子任务结果返回后，单仓审查结果各自保存为独立报告，联调结果单独生成联调报告（详见步骤 7、步骤 9）。

### 步骤 7：分别执行单仓代码审查并生成独立报告

按 [references/review_process.md](../references/review_process.md) 分别对前端仓库和后端仓库执行：

- 执行前置过滤，跳过废弃/旧文件与文件夹。
- 按检查维度逐项审查。
- 问题分级：严重bug、注意问题、一般问题、轻微问题。
- 跳过已忽略与误报问题。

**单仓审查结果各自保存为独立文件**，文件名格式：
- 前端：`<检测日期>-<当前大模型的名称>-前端代码审查报告.md`
- 后端：`<检测日期>-<当前大模型的名称>-后端代码审查报告.md`

保存到各自仓库的 `docs/code_reviews/` 目录，作为常规单仓报告处理（可被后续审查的 `fixed/` 扫描流程正常识别）。

### 步骤 8：执行跨仓联调一致性检查

按 [references/cross_repo_integration_checks.md](../references/cross_repo_integration_checks.md) 执行：

- API 路由与方法一致性。
- 请求参数一致性。
- 响应结构一致性。
- 状态码与错误格式一致性。
- 类型/codegen 一致性（含生成文件过期检查）。
- 鉴权与权限一致性。
- 分页/过滤/排序约定一致性。
- 命名与语义对齐。
- Mock 与真实 API 一致性（仅当存在 Mock 数据时）。

### 步骤 9：生成联调报告并保存到主仓库

按 [references/report_delivery.md > 跨仓库联调审查报告保存规则](../references/report_delivery.md#跨仓库联调审查报告保存规则) 执行：

- 生成联调一致性问题报告（仅含联调问题详情与两端问题统计摘要）。
- 在报告中引用前端/后端单仓详细报告的文件路径。
- 保存到主仓库的 `docs/code_reviews/` 目录。
- 忽略与误报清单 `ignored_issues.md` 与联调报告一同保存到主仓库。
- 远程场景下仅对联调报告和忽略与误报清单执行 git 提交并推送（单仓报告已在步骤7各自推送）。
- 推送失败时执行重试与降级通知。

### 步骤 10：发送审查通知

按 [references/report_delivery.md > 通知机制](../references/report_delivery.md#通知机制) 输出审查概要：

- 前端问题统计。
- 后端问题统计。
- 联调一致性问题统计。
- 三份报告路径或链接：前端单仓报告、后端单仓报告、联调报告。

## 定时触发模式

跨仓库联调审查也可由定时任务触发，此时在执行步骤 3 之前，先按 [workflows/scheduled_workflow.md](scheduled_workflow.md) 的逻辑对前端仓库和后端仓库分别执行版本检查：

1. 检查本地是否有未提交修改，若有则撤销。
2. 分别获取前端和后端的远程最新 tag / HEAD。
3. 任一仓库存在新版本：执行 `git fetch origin --tags` 后继续本工作流步骤 2-10。
4. 两仓均无变化：强制终止流程，反馈「前端与后端版本均未变化，跳过本次跨仓库联调审查」。

> 定时任务前缀仍使用 `【定时自动审查任务】`。

---

## 与现有工作流的关系

- 手动触发跨仓审查：复用 `manual_workflow.md` 中步骤 4-9 的单仓审查逻辑，前后端各执行一次。
- 定时触发跨仓审查：复用 `scheduled_workflow.md` 的版本检查逻辑，再进入本工作流。
- 本工作流**不替代**现有工作流，而是作为第三种独立工作流存在。
