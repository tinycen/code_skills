# 前后端跨仓库联调代码审查重构方案

## 背景

当前 `code-review` Skill 的工作流（手动触发、定时触发）均面向**单一仓库**设计，审查维度集中在代码规范、命名、逻辑、质量等单仓内部问题。随着项目规模扩大，同一业务功能往往由独立的前端仓库与后端仓库共同实现，仅对单仓审查无法发现以下关键风险：

- 前端调用的 API 路径、方法、参数与后端接口定义不一致。
- 后端返回的数据结构、字段类型、状态码与前端类型定义/处理逻辑不匹配。
- 前后端对同一业务实体的命名、枚举值、错误码理解不一致。
- OpenAPI/TypeScript 类型生成与实际实现不同步。
- 鉴权、分页、过滤、排序等约定在两端实现不统一。

因此需要在现有工作流基础上，新增一套**跨仓库联调审查能力**。

---

## 设计目标

1. **复用而非重写**：新工作流复用现有手动/定时工作流的单仓审查步骤，避免重复定义。
2. **职责清晰**：联调审查的检查维度、报告模板、保存规则分别独立成文，不混入 `review_process.md`。
3. **一份核心报告**：以统一的《前后端联调审查报告》作为最终交付物，联调问题集中呈现。
4. **默认保存规则可兜底**：当用户未指定主仓库且当前目录不属于任一被审仓库时，自动将报告保存到**问题数量更多**的仓库。
5. **向后兼容**：现有单仓工作流、报告模板、忽略清单机制不受影响。

## 工作流设计

`cross_repo_integration_workflow.md` 在手动触发与定时触发两种模式下均适用。

### 触发条件

必须**同时满足**以下两个条件才使用本工作流：

1. 用户显式指明了两个仓库的**前后端对照关系**，即明确告知“这是前端仓库，这是后端仓库，需要审查它们之间的联调一致性”。
   - 仅提供两个仓库地址（如“审查 A 仓库和 B 仓库”）不足以触发本工作流，此时应分别走单仓审查。
   - 触发话术示例：
     - “审查前后端联调一致性”
     - “检查前端仓库 X 和后端仓库 Y 的接口是否对得上”
     - “看看前端请求和后端返回是否一致”
2. 提供了前端仓库与后端仓库的地址/路径，或定时任务配置中同时指定了这两个仓库。

> **禁止推断**：不得因为用户一次提供了两个仓库就默认它们是前后端关系。必须由用户显式声明对照意图。

### 输入参数

| 参数 | 必填 | 说明 |
|------|------|------|
| 前端仓库地址/路径 | 是 | SSH 地址或本地绝对路径。 |
| 后端仓库地址/路径 | 是 | SSH 地址或本地绝对路径。 |
| 主仓库（报告保存目标） | 否 | 用户可指定报告保存到前端或后端仓库。 |

以下**不作为输入参数**，由审查过程中自动发现：

- **OpenAPI / Swagger / 接口定义文件**：扫描后端仓库常见位置（如 `docs/openapi.yml`、`openapi.json`、`api/schema/` 等）自动定位，并校验其内容是否与后端实际路由/模型一致（发现定义文件过期的风险）。
- **前端 API Client 生成目录**：扫描前端仓库常见生成目录（如 `src/api/generated/`、`src/services/`、`api/` 等）自动定位，并校验生成类型是否与实际后端实现同步。
- **Mock 数据目录/文件**：扫描前端仓库中的 mock 文件或 mock 服务配置，仅在存在时参与审查。

### 执行步骤

```
1. 参数识别
   ├── 确认用户显式要求前后端联调审查（触发条件校验）
   ├── 确定前端仓库、后端仓库
   └── 确定主仓库（按“保存规则”推导）

2. 自动发现辅助文件
   ├── 后端：扫描 OpenAPI / Swagger / 接口定义文件
   ├── 前端：扫描 API Client 生成目录/文件
   └── 前端：扫描 Mock 数据/服务（存在时）

3. 获取代码（远程场景）
   ├── 分别克隆/更新前端仓库
   └── 分别克隆/更新后端仓库

4. 获取版本信息
   ├── 前端：最新 tag / commit
   └── 后端：最新 tag / commit

5. 分别执行单仓审查
   ├── 前端：按 manual_workflow.md / scheduled_workflow.md 步骤 4-9 执行
   └── 后端：按 manual_workflow.md / scheduled_workflow.md 步骤 4-9 执行
   （生成单仓审查结果，作为统一报告的子章节，不单独输出文件）

6. 执行跨仓联调一致性检查
   └── 按 cross_repo_integration_checks.md 执行

7. 确定主仓库并按规则保存报告
   └── 按 report_delivery.md > 跨仓库联调审查报告保存规则 执行

8. 发送审查通知
   └── 输出概要、报告路径、联调问题数量
```

### 与现有工作流的关系

- 手动触发跨仓审查：复用 `manual_workflow.md` 步骤 4-9，但前后端各执行一次。
- 定时触发跨仓审查：复用 `scheduled_workflow.md` 的版本检查逻辑，前后端分别检查是否有新版本，任一仓库有变化即执行完整审查；两仓均无变化则跳过。

## 联调审查维度

详见 `references/cross_repo_integration_checks.md`。核心维度如下：

| 维度 | 检查内容 |
|------|----------|
| **API 路由与方法** | 前端请求的路径、HTTP 方法是否与后端路由定义一致；是否存在前端调用已删除/未暴露接口。 |
| **请求参数一致性** | 必填字段、字段命名、参数类型、默认值、传递方式（path/query/body/header）是否一致。 |
| **响应结构一致性** | 返回字段、嵌套结构、数组元素类型、空值处理是否与前端类型定义/使用一致。 |
| **状态码与错误格式** | 成功/失败状态码约定、错误码枚举、错误提示字段是否一致。 |
| **类型/codegen 一致性** | 自动发现后端 OpenAPI/Swagger 文件与前端生成的 TypeScript 类型；检查生成文件是否与后端实际实现同步，是否存在生成文件过期、字段缺失或类型不匹配。 |
| **鉴权与权限** | Token 传递方式、刷新机制、权限字段命名、未授权处理是否一致。 |
| **分页/过滤/排序** | 参数命名（page/size/offset/limit/order_by）、返回值包装结构是否一致。 |
| **命名与语义对齐** | 同一业务实体在前后端的命名、枚举值是否统一。 |
| **Mock 与真实 API 一致性** | 仅当前端仓库存在 Mock 数据/服务时执行。检查 Mock 数据字段、状态码是否与真实后端一致，是否存在仅 Mock 支持而真实后端未返回的字段。Mock 不存在时本维度跳过。 |

## 报告保存规则

本规则补充至 `references/report_delivery.md`。

### 核心原则

跨仓库联调审查只生成**一份统一报告**作为正式交付物，避免前后端问题被拆散。单仓审查结果作为该报告的子章节出现，不默认生成独立的单仓报告文件。

### 主仓库确定优先级

报告最终保存到主仓库的 `docs/code_reviews/` 目录下。

1. **用户指定优先**：用户明确说“保存到前端仓库”或“保存到后端仓库”，严格按用户要求。
2. **当前目录优先**：若当前工作目录属于前端或后端仓库之一，则保存到当前目录所在仓库。
3. **问题数量兜底**：若用户未指定且当前目录不属于任一仓库，则比较两端**问题总数（单仓问题 + 联调问题中涉及该仓库的问题）**，保存到问题数量更多的仓库。
4. **完全平局**：若问题数量相同，默认保存到**后端仓库**（API 契约通常以后端为权威源）。

### 报告命名

在原有命名规则前增加场景前缀：

```
<检测日期>-<当前大模型的名称>-前后端联调审查报告.md
```

例如：`2026-07-29-Claude-前后端联调审查报告.md`

### 报告保存内容

统一报告至少包含：

- 前端仓库基本信息（名称、版本、截止提交）
- 后端仓库基本信息（名称、版本、截止提交）
- 前端单仓问题统计与列表
- 后端单仓问题统计与列表
- 联调一致性问题统计与列表
- 辅助文件发现记录（OpenAPI、生成文件、Mock 文件等）

> 报告中不展示忽略清单内容。忽略清单单独维护于 `ignored_issues.md`。

### 忽略清单

`ignored_issues.md` 同样保存到主仓库的 `docs/code_reviews/` 目录。清单中的文件路径需标注所属仓库，例如：

```markdown
- **文件路径**: `frontend/src/api/user.ts`
- **关联文件**: `backend/app/routers/user.py`
```

### 远程推送

远程对话/插件场景下，仅对主仓库执行 `git commit && push`，报告文件与忽略清单一并提交。推送失败逻辑与现有 `report_delivery.md` 一致。

## 报告模板

详见 `references/templates/cross_repo_report.md`。与现有单仓模板相比，主要变化：

1. **基本信息表**扩展为两个仓库：

   | 项目 | 前端 | 后端 |
   |------|------|------|
   | 仓库名称 | `frontend` | `backend` |
   | 检测版本 | `1.2.3` | `2.0.1` |
   | 截止提交 | `abc1234` | `def5678` |

2. **问题统计**拆为三行：

   | 级别 | 前端 | 后端 | 联调一致性问题 |
   |------|------|------|----------------|
   | 🔴 严重Bug | x | x | x |

3. 新增**联调一致性问题**独立板块，问题描述中同时给出前端与后端的相关文件路径和行号。
